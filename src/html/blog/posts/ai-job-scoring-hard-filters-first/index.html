In part 1 we explained why we built Job Hunter: a freelancer's real problem is not finding jobs, it is deciding quickly which few are worth a proposal. This post is about the part that makes that decision. When people ask us about AI job scoring for Upwork, they usually expect us to say "we send every job to a large language model and it tells you what is good". That is not what we do, and the reasons are worth explaining.

Our pipeline has two stages. First, hard filters in plain code throw out every job that breaks a rule the freelancer has set. Second, a model scores only the jobs that survived, from 0 to 100, and it has to say why. The order matters, and so does the "why".

Why not let the model decide everything?

It is tempting. A model can read a job description, understand the client's tone, and guess whether the work fits your profile. So why not ask it about the budget and the client rating too?

Because some questions have exact answers, and a model is the wrong tool for exact answers. If a freelancer says "no fixed-price jobs under a certain amount", that is a comparison of two numbers. If they say "skip jobs that already have more than a set number of applicants", that is another comparison. A model will get these right most of the time. Most of the time is not good enough for a rule the user wrote down explicitly. One job that slips through and breaks the user's own rule damages trust in every score that follows.

There is also cost and speed. Every model call takes time and money. A saved search can return many jobs, and a large part of them fail a simple rule. Sending those to a model means paying to learn something a single if statement already knows.

Stage 1: hard filters in code

Job Hunter fetches jobs from the user's own saved searches through the Upwork GraphQL API. Each job then goes through a set of hard filters, all of them plain PHP in our Laravel 12 application:

  • Budget. The user sets a minimum for fixed-price jobs and a minimum hourly rate for hourly jobs. If the job is below the line, it stops here.
  • Client rating. A client with a rating below 4.0 is filtered out.
  • Number of applicants. The user sets a maximum. If a job already has more proposals than that, there is little point in scoring it.
  • Country. Clients must be in North America or Europe, for time zones, language and invoicing. This is a fixed list of regions, so it is a list lookup.
  • Posting age. A job that has been open for more than two weeks (the default) is skipped, because the client has usually hired or stopped reading.

Each filter is deterministic. The same job with the same settings always gets the same result, and we can write a unit test for each rule. When a filter rejects a job, we keep a short record of it with the rule that rejected it, and the user can see that reason in the job list. That sounds like a small detail, but it is the first half of explainability: if a user asks "why did I never see that job?", the answer is a fact, not a guess.

The filters run right after each fetch, before a job is even stored as a real posting. Only the jobs that pass are handed to queued jobs on Redis with Horizon for scoring, so the queue waits on the model in stage 2, and only for jobs that deserve it.

If you want to set these rules up well, we wrote a separate guide on filtering Upwork jobs by budget, rating and country. It goes into which thresholds make sense and what to avoid.

Stage 2: the model scores what passed

Only the jobs that passed every filter reach the model. Here the questions are fuzzy, and a model is good at fuzzy questions: does this description match the freelancer's skills? Is the scope clear or vague? Does the client describe a real project or a wish list? Is this a job the freelancer could win and deliver well?

The model returns a score from 0 to 100. We use OpenAI and Anthropic models behind one interface, so we can compare them and change them without touching the rest of the pipeline. The prompt gets the job text, the freelancer's profile and the basic job facts, such as budget and client details, because they are part of the fit. But the yes or no on the hard rules stays in code: if the model complains about a budget or a country that the filters already accepted, the code removes that complaint from the result. Those questions are closed.

Take our invented demo job: "Laravel developer for a booking platform", fixed price, client in Germany. Germany is in the allowed regions, and assume the budget passes. The filters let it through. The model now reads the description against a profile that lists Laravel and booking systems, and it might give a high score with reasons like "core stack matches", "scope is described in concrete features" and "booking domain experience in profile". If the description were two lines with no details, the same job would score lower, and the reason would say so.

Why the score must be explainable

A number alone is not useful. If Job Hunter says "73" and nothing else, the freelancer has two options: trust it blindly or read the whole job anyway. In the second case, we saved them nothing.

So every score comes with short reasons: what pushed it up, what pulled it down. We ask the model for a JSON answer: the score, a short summary, sub-scores for skills, budget, client and clarity, and two lists of reasons, positive ("green flags") and negative ("red flags"). If the answer cannot be parsed as JSON, the call fails and the queued job tries again later. The summary and the reasons are shown in the alert and in the dashboard next to the score.

Explainable scores help in three ways:

  • The user can disagree quickly. If a reason is wrong ("no mobile experience", when the profile clearly lists it), the user sees it at once and can fix the profile or ignore the score.
  • We can debug the prompt. When scores look odd, the reasons show us what the model paid attention to. A bare number would give us nothing to work with.
  • Trust grows in the right direction. A freelancer should trust the score because the reasons keep making sense, not because a number looks precise.

Explainability is also why the split between the two stages is so clean. Every "no" from stage 1 has an exact cause from code. Every score from stage 2 has reasons in words. There is no step where a job disappears and nobody can say why. We go deeper into how the score is built and how to read it in our guide to reading Upwork job scores.

What we learned

A few lessons from building this:

  • Put every rule the user can state exactly into code. If a setting has a number or a list, it belongs in a filter, not in a prompt.
  • Keep the model's job narrow. The model answers "how well does this fit?", nothing else. A narrow question gives more stable scores.
  • Store the reason with the result. For filters, the rule that rejected the job. For scores, the reasons. Without them, support questions become guesswork.
  • A score is advice, not a decision. Job Hunter does not apply for anything. The user reads the job, the score and the reasons, and submits a proposal on Upwork by hand if they want to.

That last point leads to the next stage. Once a job has a good score, Job Hunter writes a cover letter draft and answers to screening questions. How we keep those drafts useful and why we never submit them is the topic of part 3: AI cover letters for Upwork.
